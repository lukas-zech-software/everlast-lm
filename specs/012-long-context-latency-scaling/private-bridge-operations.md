## Retained clock acquisition before bridge bootstrap

This bridge transports and verifies retained calibration; it does **not** measure/attest Cloud Run's host clock. There is no assumption that offset=0. Avoid a circular bootstrap: acquire trusted clock bounds independently **before** pinning execution metadata/deploying the bridge. The required external procedure is:

- At a recorded UTC instant, retain operator host clock evidence from an approved authenticated time source (for example, NTS-backed chrony tracking/source output) including signed/source identity, measured offset `operatorClock−UTC`, worst-case root-dispersion/error bound, sample interval and expiry. Retain the raw evidence privately and hash it in the qualification document.
- Independently obtain trusted serving/provider clock characterization covering the exact candidate/revision/runtime domain and intended window: measured `serverClock−UTC`, maximum error/uncertainty, source identity, method and validity interval. A statement that a platform “synchronizes time,” an HTTP proxy Date header, an operator signature or a client timestamp is insufficient to bound actual application Date.now(). The owner must verify the independent source and retain its evidence/hash. This run has **no** such Cloud Run measurement/attestation, so this prerequisite is UNAVAILABLE.
- Derive `offset_ms=(serverClock−UTC)−(operatorClock−UTC)` and conservative `uncertainty_ms=serverError+operatorError+measuredDriftAllowance`; it must be<=1000ms. Use the overlap of both independently evidenced validity intervals, converted into CLIENT-domain epoch, for measured_at_ms/expires_at_ms; `measurement_id` identifies the retained measurement set. Do not subtract uncertainty from observed performance or change any threshold. Review and freeze this exact five-field calibration JSON, SHA256(JSON.stringify(parsedCalibration)), qualification record, fixture and execution metadata before the approved deployment. Both server and CLI use those exact retained bytes/fields. The boot-specific challenge then binds this already retained calibration hash to the actual boot, removing any dependency on reading a challenge to invent calibration.

No external attestation acquisition tool or private clock-only bootstrap measurement protocol is implemented here. If an independently trustworthy serving-clock bound cannot be obtained, that measurement protocol is **additional required implementation**, not a zero-offset default, cloud-only waiting flag, or a claimed clock pass. Existing010collection also needs this same measured prerequisite. Actual live operational completion remains open until a defensible bound exists. Mapping/offset/expiry tests only characterize the verifier, not Cloud Run timekeeping.
